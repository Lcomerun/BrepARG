# V13 Generation Quality Recovery ExecPlan

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds. This document follows `PLANS.md` in the repository root.

## Purpose / Big Picture

The user wants generated CAD models that are worth showing in an AAAI paper, not merely STEP files that pass a validator. The current generated examples are mostly simple primitives, thin plates, rings, and long bars, and some outputs are visually broken even when a STEP file is saved. This plan defines how to move from the current weak generation results toward a stronger pipeline by diagnosing and improving the three layers that can fail: the VQ-VAE geometry decoder, the sequence/data preparation, and the AR generator.

The visible end state is a new set of generated STEP files and rendered images that include nontrivial, visually plausible, strict BREP-valid CAD models. A future agent should be able to follow this plan from a fresh session, run the diagnostics, train the right stage first, and decide from evidence whether VQ-VAE, sequence length, AR training, or sampling remains the bottleneck.

## Plan of Work

The first milestone is to make quality visible. Use `render_step_directory.py` after every generated or validation reconstruction run. Never judge generation quality only from `step_saved` or `brep_valid` counts. A run is not paper-quality unless the contact sheet contains visually plausible CAD models that are more complex than simple primitives.

The second milestone is to isolate VQ-VAE quality. Run validation reconstructions for shortest, random, longest, most-face, and future source-path-backed curved-surface subsets. The existing shortest validation smoke test is too easy; it mostly proves simple examples can pass. The longest diagnostic must be tracked because it reveals complex reconstruction failures. If VQ-VAE fails complex validation rows, retrain VQ-VAE before touching AR.

The third milestone is to build better sequence training views. The existing sequence package includes long and complex models, but the AR trainer currently filters to sequences of length at most 1024. On a 48GB or 80GB rented GPU, add or configure training branches with `max_seq_len=1536` and then `max_seq_len=2048`, and record how many complex samples enter each branch.

The fourth milestone is to train AR with topology-aware weighting. The generated distribution collapses toward 4F/6E and 6F/12E. Create sampling weights or training buckets that increase the probability of complex topologies, especially 12+ and 20+ face models. Evaluate with the same fixed sampling settings and render every retained STEP.

The fifth milestone is to update the AAAI paper only after improved evidence exists. The current weak generated sheets may be used in a failure-analysis section or supplement, but not as positive examples. Main-paper figures should be selected from new, visually credible runs.

The current implementation now includes the first recovery controls. `breparg_improvements/vqvae_sampling.py` selects VQ-VAE geometry patches with optional complex-source and curved-patch fractions. `breparg_improvements/train.py` reads `NS_VQ_COMPLEX_FRACTION`, `NS_VQ_COMPLEX_MIN_FACES`, `NS_VQ_COMPLEX_MIN_EDGES`, `NS_VQ_CURVED_FRACTION`, and `NS_AR_MAX_SEQ_LEN`, writes these settings into reports or checkpoints, and leaves the old behavior unchanged when the fractions are zero. `tools/run_vqvae_complex_recovery.ps1` and `tools/run_vqvae_complex_recovery.sh` are the recommended starting commands for the next VQ-VAE continuation branch, depending on whether the run is local Windows or rented Linux. `tools/run_ar_v13_long_context.sh` is the Linux AR entry point for 1536/2048 experiments.

## Validation and Acceptance

Quality recovery is not accepted merely because validation CE improves. It is accepted only when a generated sample run of at least 100 attempts produces retained STEP files that are visually more complex and more credible than the current primitive-like outputs, with a documented strict BREP-valid rate and contact sheet.

The VQ-VAE milestone is accepted when validation-longest reconstruction improves substantially over the current 3/10 strict BREP-valid baseline and the rendered outputs no longer show widespread broken surfaces or stray curves. Operationally, the candidate run should produce a benchmark summary whose promotion decision is `promote_for_ar_rebuild`; a held checkpoint should not be used to rebuild AR sequences or paper-positive figures.

The AR milestone is accepted when generated topology distribution no longer collapses mainly to 4F/6E and 6F/12E, and when samples with 12+ and 20+ faces appear as visually plausible models rather than degenerate surfaces.

The paper milestone is accepted only when positive qualitative figures are selected from improved runs, and current weak outputs are either removed from the main paper or clearly labeled as failure-analysis examples. Operationally, a generated run should not provide positive figures unless its `generated_quality_summary.json` decision is `promote_as_paper_candidates`, `paper_figure_candidate_audit.json` reports `ready_for_paper_figure_review`, and a separate human-review JSON records `decision=approved_for_paper_figures` with `approved=true` after contact-sheet inspection.

## Idempotence and Recovery

All reconstruction and rendering runs are additive because they write timestamped or named directories under `local_runs/reconstruction_eval`. Re-running a diagnostic with the same `--run-name` can append or overwrite files in that run directory, so use a new run name for comparisons unless intentionally regenerating the same artifact. Rendering is safe to repeat; it overwrites PNGs under the run's `renders` directory without touching STEP files.

Do not delete existing checkpoints or reconstruction directories. If a rented-server training run is copied back, place it under a new branch directory in `local_runs/ar_training/train_outputs` or `ABC/processed/train_outputs` and record the source server, command, checkpoint, and metrics in this ExecPlan.
